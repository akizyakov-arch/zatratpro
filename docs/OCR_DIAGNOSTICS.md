# Распознавание: структура и диагностика

## Общая цепочка Telegram/MAX

`DocumentFlow.receive` → загрузка bytes → `document_processing.recognize_document`:

1. Фото: `prepare_image` → JPEG. PDF: ограниченный render worker → JPEG страниц.
2. `recognition_runtime.extract_page` → выбранный recognizer → обычный OCR-текст.
3. `DeepSeekService.extract_document` → поля документа → `DocumentSchema` и проверки.
4. Выбор проекта/сохранение через общий `DocumentFlow`.

В OCR.space multipart POST входят только `apikey=OCR_SPACE_API_KEY`, `language=rus`,
`OCREngine=2` и бинарный JPEG в `file`. Текстовые инструкции, ключ и JSON Vision
DeepSeek не отправляются в OCR.space. Тест разбирает фактический MIME-запрос HTTPX.

## Политика времени и повторов

- `OCRSpaceService` выполняет ровно один HTTP-запрос за вызов, без скрытого цикла.
  HTTP connect timeout — 20 секунд, остальные HTTP timeout — 120 секунд.
- `recognition_runtime.extract_page`: максимум две попытки по 120 секунд с паузой
  3 секунды. Используется фото и каждой отрендеренной PDF-страницей.
- Повторяются только таймаут или временная E101. Ключ, HTTP-отказ и неверный JSON
  возвращают явную ошибку без автоматического повтора.
- Специфический повтор обрезанного ответа DeepSeek Vision с увеличенным бюджетом
  сохранён внутри его общего лимита 115 секунд. Провайдер сам не переключается.
- Внешние бюджеты PDF 600 секунд, всего сценария 750 секунд, структурирования
  DeepSeek 120 секунд сохранены. Качество JPEG/PDF и правила сумм не изменены.

Ранее у OCR.space были три внутренних HTTP-попытки, а у фото ещё два внешних
deadline. Для фото получалось около 243 секунд; новые две попытки сохраняют этот
верхний бюджет, но управляются одним слоем. Для PDF внутренний цикл 3×120 заменён
единой политикой 2×120, с прежним общим бюджетом PDF. Это явное изменение повторов,
а не улучшение качества изображения или доказательство исправления VPS-сети.

`RecognitionError` содержит безопасное сообщение, код и флаг возможности повтора.
`OCRSpaceError` сохранён как совместимый alias; существующие фронты продолжают
показывать эти ошибки. Отмена task не превращается в повторную загрузку.

## Логи

- `document_ocr_start/done/failed`: провайдер, попытка, байты и размеры изображения,
  время и безопасный код ошибки; общий для фото/PDF.
- `ocr_space_start/response/failed/cancelled`: случайный ID запроса, HTTP-статус,
  время, код ошибки. Cancelled может означать внешний deadline или остановку процесса.
- `ocr_space_transport`: только имена разрешённых событий HTTPX/httpcore — подключение,
  TLS, окончание отправки тела запроса, получение заголовков ответа.
- `document_parse_start/done/failed`: отдельный этап структурирования DeepSeek.

Тело, изображение, текст, имя файла, ключи и содержимое `trace.info` не логируются.
HTTP 200 ещё не означает успех: ошибки внутри JSON, E550 и неверная структура
проверяются отдельно. В частности, E550 распознаётся и при HTTP 200.

Если виден `send_request_body.complete`, файл передан HTTP-транспортом; отсутствие
`receive_response_headers.complete` до таймаута указывает на последующее ожидание,
но само по себе не отделяет сеть от очереди OCR.space. Эти логи не доказывают,
что сервер обработал всё тело запроса. Реальный скан и синтетический тест сравнивать
нужно с одинаковыми параметрами и из того же контейнера.

```bash
docker logs --since=10m --tail=150 zatratpro-bot 2>&1
docker logs --since=10m --tail=150 fiinops-zatratpro-max-1 2>&1
```

MAX пока использует последовательный poller: эта работа не добавляет фоновую
очередь и не устраняет неизвестную внешнюю причину зависания на VPS.

## Обновление

Новых переменных .env и миграций нет. Собрать и пересоздать оба бота на одной
версии, сохранив Compose project, .env и том БД. После установки проверить один
реальный скан и изучить сетевые этапы. Пересоздание базы не требуется.
