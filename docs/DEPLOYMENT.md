# Запуск FIINOPS по HTTPS

Готовая конфигурация рассчитана на сервер с Docker Compose и публичным доменом.
Панель и обновлённый Telegram-бот работают с одной PostgreSQL. Caddy получает
и продлевает сертификат, перенаправляет HTTP на HTTPS и хранит сертификаты
в отдельном постоянном томе.

## Адрес и настройки

1. Направьте DNS A домена панели на публичный IPv4 сервера. Если есть AAAA,
   он также должен вести на этот сервер. На сервере нужны входящие порты 80 и 443.
2. В каталоге проекта скопируйте `.env.production.example` в `.env`, задайте
   `WEB_DOMAIN` без схемы/пути, ID владельца и рабочие секреты. Ограничьте доступ:

   ```bash
   chmod 600 .env
   ```

3. Проверьте настройки и DNS:

   ```bash
   python scripts/check_deployment.py --check-dns --server-ip АДРЕС_СЕРВЕРА
   docker compose -f docker-compose.yml -f docker-compose.https.yml config --quiet
   ```

Секреты не передаются в GitHub и не выводятся проверкой. На обычном VPS задаются
его собственные реальные секреты: значения-заполнители прокси облачной среды
переносить на VPS нельзя. `WEB_ORIGIN`, допустимый Host, secure cookies и адрес
доверенного proxy вычисляются HTTPS-конфигурацией из `WEB_DOMAIN`.

Подсеть proxy по умолчанию `172.29.248.0/24`, адрес Caddy `172.29.248.2`, панели —
`172.29.248.3`. Если подсеть занята, измените `FIINOPS_PROXY_SUBNET`,
`FIINOPS_PROXY_IP` и `FIINOPS_WEB_IP` вместе.
Панель доверяет заголовкам только этого proxy. PostgreSQL не публикуется наружу;
порт 8080 доступен только на loopback сервера.

## Обновление существующей установки Docker Compose

Сначала создайте и проверьте резервную копию уже работающей базы:

```bash
python scripts/backup_database.py
```

Скрипт сохраняет архив с правами 0600 вне репозитория и проверяет его через
`pg_restore --list`. При ошибке неполный архив удаляется; сервисы не меняются.
Если существующая база не найдена в этом Compose, скрипт завершится с ошибкой,
вместо создания новой пустой базы.

Затем соберите образ до остановки работающих процессов:

```bash
docker compose -f docker-compose.yml -f docker-compose.https.yml build
docker compose -f docker-compose.yml -f docker-compose.https.yml stop zatratpro-bot zatratpro-web
docker compose -f docker-compose.yml -f docker-compose.https.yml up -d --wait zatratpro-web zatratpro-bot caddy
```

Перед миграциями должны быть остановлены все старые процессы бота, включая
запущенные вне Compose. Бот и панель обновляются вместе: после миграции 009
старый код привязки чеков несовместим со схемой. Возврат к старой версии требует
согласованного восстановления БД и приложения из резервной копии.

## Новая установка или перенос на другой сервер

Для новой пустой базы исходную схему создаёт PostgreSQL при первом старте:

```bash
docker compose up -d --wait zatratpro-db
```

Если переносите существующие данные, восстановите проверенную копию в эту БД
до старта приложения. База текущей облачной среды находится в отдельном runtime;
новый Compose автоматически её не подключает. Существующие данные нельзя
подменять пустым томом. Выпуск на другой сервер включает отдельный перенос БД
и отключение прежнего экземпляра polling-бота.

После создания или восстановления базы выполните сборку и запуск по командам
обновления выше. Том PostgreSQL и тома сертификатов сохраняются при перезапуске.
Для обычного обновления не используется `docker compose down -v`.

## Проверка после запуска

Откройте `https://ВАШ_ДОМЕН/healthz`: ожидается `{"status":"ok"}`. Затем откройте
панель, подтвердите вход в том же Telegram-аккаунте и проверьте компанию/роль.
Для входа используется существующий бот `WEB_BOT_USERNAME` с новым обработчиком.
Проверьте выдачу → получение в боте → чек → принятие в панели → совпадение Excel.

Автоматическое получение публичного сертификата возможно после настройки DNS
и доступности портов сервера. Временный запуск в облачной среде сам по себе
не создаёт публичного домена или постоянного хостинга.

## Выполненная проверка

25.10.2026 собран реальный образ приложения и запущен отдельный тестовый стек
PostgreSQL → веб-панель → Caddy. Проверены миграции, health checks, HTTPS,
HSTS, защищённые cookies, вход в ожидании подтверждения и отказ чужому Origin.
TLS проверялся с включённой проверкой сертификата по корневому сертификату
локального тестового CA; публичный сертификат для пользовательского домена
ещё не запрашивался. Реальные `pg_dump` и `pg_restore --list` подтвердили работу
скрипта резервного копирования. Тестовый стек и его тома удалены.

Пять проверок `test_deployment.py` покрывают отбраковку шаблонных настроек,
некорректных адресов proxy, настройки мини-приложения и удаление повреждённых/
непроверенных архивов.
