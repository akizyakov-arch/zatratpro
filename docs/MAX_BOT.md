# Первое подключение MAX

Ветка добавляет отдельный тестовый адаптер MAX к общей базе FIINOPS.
Пользователь определяется через `external_accounts(platform='max')`, а его
компания, роль, проекты и деньги остаются на прежнем внутреннем `users.id`.
Код Telegram-обработчиков в адаптер не импортируется.

## Подготовка бота и токена

Создайте бота на официальной [платформе MAX для бизнеса](https://business.max.ru/self)
или через [MAX для бизнеса](https://max.ru/business_bot), согласно доступному
вашему профилю процессу. Полученный токен относится только к MAX.

В облачной среде добавляется секрет с именем **MAX_BOT_TOKEN**, переменная
`MAX_BOT_TOKEN`, разрешённый адрес назначения **platform-api2.max.ru**.
Токен не нужно отправлять в чат, записывать в GitHub или в браузерную демопанель.
На собственном сервере можно использовать закрытый `.env` с правами 0600.

Документация MAX проверена 26.10.2026: текущий API использует новый хост
`platform-api2.max.ru`, а авторизация передаётся заголовком `Authorization`.
Параметры query для токена не используются. Запросы не перенаправляются на
другие хосты. При необходимости `MAX_CA_BUNDLE` указывает PEM-файл доверенных
корневых сертификатов; он дополняет системный trust store. Проверка TLS включена.
Сертификаты берутся из официального доверенного источника, не из сообщений бота.

Проверка токена и текущих подписок без изменения БД и получения обновлений:

```bash
python -m app.max_bot --check
```

Команда не меняет Webhook-подписки и не выводит токен. Без настроенного токена
она завершится с понятным сообщением до обращения к MAX и PostgreSQL.

## Тестовый запуск

MAX разрешает Long Polling для разработки и тестирования. Он не требует
публичного входящего адреса, поэтому подходит для первого теста в этой среде.
Для production официальная документация требует Webhook. **Webhook в этот
первый адаптер не входит**, его подключение — следующий этап.

Перед первым запуском сделайте резервную копию существующей базы. Миграция
`011_max_poll_offsets.sql` добавляет таблицу курсоров, а
`012_advance_issue_drafts.sql` — черновики выдач и идентификаторы обработанных
сообщений. Новая миграция не меняет существующие финансовые записи.
Подключение к БД должно указывать на ту же базу, что и Telegram-бот.
MAX требует только `MAX_BOT_TOKEN` и настройки `POSTGRES_*` (при необходимости
`MAX_CA_BUNDLE`). Ключи Telegram/OCR/DeepSeek и `BOT_OWNER_TELEGRAM_ID` ему не нужны.
Инициализация БД не меняет владельца. Синхронизация сохранённой роли владельца
выполняется явно при запуске Telegram; отсутствующий или нулевой ID отклоняется
без изменения ролей. Проверки полномочий Telegram и веб-панели продолжают
использовать настроенный ID владельца.

```bash
python -m app.max_bot --poll-dev
```

При действующей Webhook-подписке polling не запускается и подписка не удаляется.
Один MAX-бот может иметь только один процесс polling: это проверяется блокировкой
PostgreSQL. Разные боты имеют отдельные курсоры.

Курсор сохраняется после завершения всей страницы событий. При временной
сетевой ошибке или HTTP 429/5xx текущая страница остаётся в памяти: уже завершённые
события пропускаются, незавершённое обрабатывается повторно с новой проверкой прав.
Ответы с финансовыми данными не кешируются между попытками. HTTP 403 именно при
отправке сообщения означает недоступность диалога: ответ пропускается с записью
без содержимого сообщения в журнал, остальные пользователи обслуживаются дальше.
HTTP 401, прочие неизвестные 4xx, ошибки обработки и БД завершают процесс;
403 при чтении обновлений также считается ошибкой всего подключения.

При обнаружении разрыва соединения, удерживающего PostgreSQL-блокировку, текущая
работа отменяется и процесс завершается. Автоматического продолжения без блокировки
нет. Новый процесс получает блокировку заново и читает сохранённый курсор.

Подтверждение получения денег защищено идемпотентностью финансового ядра.
Повтор `/link` с тем же действующим кодом от того же MAX-аккаунта возвращает
существующую заявку и не расходует лимит новых попыток. Другой аккаунт,
отменённая заявка и истёкший код отклоняются. Подтверждение исходным аккаунтом
остаётся обязательным; повтор заявки не выдаёт права.

Ограничения тестового режима: после аварийного перезапуска возможны повторные
ответы, в том числе части длинного ответа. Пропущенный ответ в недоступный диалог
автоматически не пересылается. На первом запуске без курсора MAX отдаёт последнее
событие, а не архив; потеря процесса до первого сохранения курсора может потерять
необработанное событие. Прогресс внутри страницы хранится в памяти, не в БД.
Постоянная эксплуатация требует Webhook с долговечной очередью и политикой
повторной доставки — это отдельный следующий этап.

## Связать существующего пользователя

1. В Telegram: «Мой профиль» → «Код для подключения MAX».
2. В личном диалоге с новым MAX-ботом: `/link КОД`.
3. Вернуться в исходный Telegram-профиль и подтвердить показанный MAX-аккаунт.
4. В MAX отправить `/start` или `/profile`.

До шага подтверждения финансового доступа нет. Сам `/start` не регистрирует
дубликат пользователя, не назначает компанию или роль. Invite-код компании
не является кодом привязки аккаунта. Групповые сообщения и сообщения от ботов
игнорируются; ID из текста или пересланного сообщения не определяет пользователя.

## Доступные команды первого этапа

| Команда | Результат |
| --- | --- |
| `/start`, `/help` | Список команд или инструкция подключения |
| `/join КОД` | Вступить в компанию по приглашению без Telegram |
| `/invite` | Руководителю: пригласить сотрудника |
| `/link КОД` | Привязать MAX к существующему профилю Telegram |
| `/profile` | Связанные аккаунты и внутренний ID |
| `/projects` | Все неархивные проекты доступной компании |
| `/issue`, `/issue_resume`, `/cancel` | Новая выдача, продолжение черновика, отмена черновика (руководитель) |
| `/money` | Последние 30 выдач: свои у сотрудника, компания у руководителя |
| `/balance` | Подтверждённые остатки и задолженность компании |
| `/advance ID` | Карточка доступной выдачи и состояние расходов |
| `/receive ID` | Подтвердить фактическое получение своей выдачи |
| `/report month`, `/report week`, `/report all_time` | Денежный отчёт с теми же правилами и UTC-периодами, что в других интерфейсах |

Сотрудник не получает доступ к чужим выдачам, владелец системы автоматически
не становится руководителем компании. При отключении пользователя MAX теряет
доступ к его данным. Ответы отправляются лично аутентифицированному отправителю.

## Кнопочное меню

После привязки отправьте `/start`: доступны «Проекты», «Деньги», «Отчёты» и
«Профиль». Это нативные кнопки MAX типа `message`: нажатие отправляет подпись
как обычное сообщение пользователя. Callback-подписки и отдельный `/answers`
не нужны. Команды остаются доступны, ввод подписей вручную имеет те же права.
Получатель ответа всегда определяется аутентифицированным отправителем MAX.

«Проекты» показывает открытые проекты. «Деньги» показывает последние 30 выдач
страницами по пять, кнопки карточек выдач и «Остаток». «Отчёты» предлагает неделю,
месяц или всё время (UTC). «Профиль» показывает связанные аккаунты.

В карточке своей ожидающей выдачи есть «Подтвердить получение»: открывается
проверка суммы и проекта с отдельной кнопкой «Да, получил». До этой кнопки
учёт не изменяется. Руководитель не подтверждает получение за сотрудника.
Повторное нажатие не создаёт второе событие; отмена выдачи, отключение пользователя
и изменение доступа проверяются в общем ядре при каждом действии.
Руководителю доступна «Деньги → Выдать деньги»: сотрудник → проект → сумма →
назначение (необязательно, кнопка «Без назначения») → подтверждение. На экране подтверждения видны сотрудник, проект,
сумма и назначение. До нажатия «Выдать» финансовая запись не создаётся; после
создания сотрудник отдельно подтверждает получение денег.

Черновик действует 15 минут и хранится в PostgreSQL отдельно от Telegram-сценариев.
«Продолжить выдачу» возвращает текущий шаг после навигации или перезапуска;
`/cancel` и «Отмена» отменяют незавершённую заявку. Новая заявка отменяет предыдущий
черновик, но не отменяет уже созданные выдачи. Номера заявок на кнопках защищают от
действий из старого диалога. Сумма вводится обычным сообщением. Назначение можно ввести текстом или пропустить кнопкой «Без назначения».
Повтор сообщения не переводит черновик на следующий шаг второй раз.

Подтверждение создаёт выдачу через общее финансовое ядро в одной транзакции с
завершением черновика. Повторное и одновременное подтверждения не создают дубль.
Права руководителя, компания, активность сотрудника и проекта проверяются заново.
Сотруднику и владельцу без роли руководителя выдача недоступна. Это запись
фактической выдачи в учёте, а не банковский перевод.

Кнопки навигации возвращают к деньгам или главному меню. У непривязанного
пользователя финансовые кнопки не показываются. В длинных ответах клавиатура
прикрепляется только к последнему фрагменту. Использование старых сообщений
не обходит текущие права; недоступная страница предлагает открыть выдачи заново.

## Следующие этапы

- HTTPS Webhook с проверкой секретного заголовка, очередью и повторной доставкой.
- Согласование расходов/возвратов через MAX.
- Загрузка фото через MAX и подключение к общему документному/OCR-сценарию.
- Полный набор административных действий и уведомления MAX.

Тесты используют поддельный HTTP transport MAX и отдельные временные PostgreSQL.
Реальный токен и реальное сообщение MAX для автоматических тестов не нужны.
Секрет подключён, но проверка реального API ранее возвращала HTTP 502.
Рабочий MAX-бот не запущен; внешний доступ будет проверен отдельно.

Критерии приёмки рефакторинга:

- отказ одного получателя не останавливает другие диалоги;
- после потери блокировки старый процесс не продолжает polling, новый может стартовать;
- временный сбой не повторяет уже завершённые события в текущем процессе;
- повтор привязки не создаёт событие или пользователя повторно и не обходится без подтверждения;
- отключение пользователя проверяется заново при повторной обработке;
- MAX запускает БД и читает общий учёт без ключей других интеграций;
- запуск MAX сохраняет роль владельца даже при отсутствующей или отличающейся настройке ID;
- справочник проектов использует общий сервис проверки активного членства;
- полный набор тестов Telegram, MAX, финансового ядра и веб-панели проходит.

Проверка после рефакторинга 26.10.2026: **188 тестов прошли без ошибок и пропусков**,
включая 34 проверки MAX (15 новых сценариев надёжности). Проверены реальный разрыв
тестового PostgreSQL-соединения, освобождение блокировки, повтор привязки после
перезапуска, ошибки отправки, отзыв доступа между попытками и независимый запуск
БД без ключей интеграций. `pip check`, компиляция Python и `git diff --check` прошли.

После добавления меню: **196 тестов прошли без ошибок и пропусков**, включая
42 проверки MAX. Восемь новых тестов покрывают клавиатуру официального формата,
длинные ответы, переходы, периоды, страницы выдач и повторные/запрещённые
подтверждения получения. Реальный API MAX для этих тестов не вызывался.

После добавления выдачи руководителем: **205 тестов прошли без ошибок и пропусков**,
включая 51 проверку MAX. Девять новых сценариев проверяют полный диалог, повторные
и одновременные подтверждения, откат транзакции, восстановление черновика,
ошибочные суммы, отмену, срок действия, старые кнопки и проверки доступа.
Миграция 012 проверена на временных БД; в рабочей базе пока не применялась.

Официальные источники:
[API](https://dev.max.ru/docs-api),
[Long Polling](https://dev.max.ru/docs-api/methods/GET/updates),
[сообщения](https://dev.max.ru/docs-api/methods/POST/messages),
[схема событий](https://github.com/max-messenger/api-schema).

Подтверждение получения через MAX также ставит уведомление в общую очередь:
его получает оформивший выдачу руководитель в привязанный Telegram.

## TLS и актуальный адрес API

По [официальной документации](https://dev.max.ru/docs-api/) и
[MAX Messenger Agent Skill](https://github.com/max-messenger/max-agents-skill)
нужно использовать `platform-api2.max.ru`, а не устаревший `platform-api.max.ru`.
Ответ 401 от старого адреса не означает, что на него следует переключать бота.

В клиент включён публичный Russian Trusted Root CA из официального источника
Госуслуг; отпечаток проверен по скиллу MAX. Сертификат добавляется только в
SSL-контекст MAX, в дополнение к системным корням, без отключения TLS и
проверки имени хоста. Dockerfile копирует его вместе с каталогом app.
`MAX_CA_BUNDLE` остаётся необязательным дополнительным CA-файлом.

Детали происхождения, SHA-256 и срок действия — в
`app/max_bot/certs/README.md`. В диагностике различаются тайм-аут, TLS и
ошибка соединения; исходные исключения с возможными реквизитами не выводятся.

### Отдельный контейнер MAX для тестового VPS

Запуск Telegram-контейнера не запускает MAX. Для тестового Long Polling
подготовлен `docker-compose.max-dev.yml`; production требует HTTPS Webhook.
Добавьте `MAX_BOT_TOKEN` в локальный `.env`, затем:

```bash
docker compose -p fiinops -f docker-compose.yml -f docker-compose.max-dev.yml build zatratpro-max
docker compose -p fiinops -f docker-compose.yml -f docker-compose.max-dev.yml run --rm --no-deps zatratpro-max python -m app.max_bot --check
```

Если авторизация успешна и webhook-подписок 0:

```bash
docker compose -p fiinops -f docker-compose.yml -f docker-compose.max-dev.yml up -d --no-deps zatratpro-max
docker compose -p fiinops -f docker-compose.yml -f docker-compose.max-dev.yml logs --tail=40 zatratpro-max
```

Используйте то же имя Compose-проекта, что у работающей БД (`fiinops` в данном
примере). Оба бота работают с одной базой и каноническими пользователями.
Существующие webhook-подписки скрипт не удаляет и при их наличии polling не
запускает. Одновременно должен работать только один MAX polling-процесс.

## Вход по приглашению без Telegram

Новый пользователь открывает MAX-бота и отправляет `/join КОД` приглашения
в компанию. Владелец создаёт приглашение руководителю, действующий руководитель
создаёт приглашение сотруднику. Код задаёт компанию и роль; отправитель не
может выбрать роль в тексте команды. Профиль создаётся с `telegram_id=NULL` и
единственным внешним аккаунтом MAX. После входа бот сразу показывает меню.

Руководитель MAX может нажать «Пригласить сотрудника» или отправить `/invite`,
а затем передать человеку готовую команду `/join КОД`. Приглашение одноразовое,
действует 72 часа; новый код сотрудника заменяет предыдущее неиспользованное
приглашение этой компании. Сотрудникам команда выдачи приглашений недоступна.

`/link` остаётся привязкой к существующему профилю Telegram; обратный путь
MAX → Telegram доступен через «Профиль → Подключить Telegram». Существующий
MAX-аккаунт повторно не создаётся. Незавершённую привязку нужно сначала
подтвердить или отменить в исходном профиле. Автоматического слияния людей нет.
Аккаунт владельца системы через приглашение не становится руководителем
компании. Сохраняются один руководитель, одна активная компания, лимит
сотрудников и запрет понижения руководителя приглашением сотрудника.

Общее принятие приглашений используется Telegram и MAX. Регистрация профиля,
назначение роли и использование кода атомарны. Неудачная попытка не оставляет
нового пользователя и не расходует приглашение. Повтор успешной команды тем
же MAX-пользователем возвращает существующее членство; использованный код
не восстанавливает исключённого участника и не возвращает прежнюю роль.
На MAX отправителя допускается пять попыток за 15 минут, включая неверные коды.

Миграция `018_max_company_invite_attempts.sql` добавляет счётчик попыток,
существующие пользователи и финансовые записи не меняются. Перед обновлением
сделайте резервную копию БД; новую миграцию применяет старт приложения.

Вход и приглашения MAX не требуют ключей Telegram/OCR/DeepSeek. Уведомления
о получении денег пока доставляются в Telegram руководителя; для руководителя
без Telegram этот канал отсутствует. Загрузка чеков и полный набор операций
Telegram в MAX этим изменением не добавляются.

## Выбор первой платформы и подключение второй

Приглашение компании общее: руководитель/сотрудник может принять его через
Telegram или MAX. Не создавайте две учётные записи для одного человека:
после первого входа подключайте второй мессенджер через профиль.

Для MAX → Telegram откройте «Профиль → Подключить Telegram». При настроенном
`TELEGRAM_BOT_USERNAME` (имя нашего Telegram-бота без @) в ответе будет готовая
ссылка `https://t.me/ИМЯ?start=link_КОД`. Перейдите по ней, затем вернитесь в
MAX, нажмите «Обновить профиль» и подтвердите именно свой Telegram ID.
Можно также отправить `/start link_КОД` или `/link КОД` вручную. Код действует
5 минут. До исходного подтверждения доступ в Telegram не выдаётся.

Глубокая ссылка обрабатывается до обычной регистрации /start, а обычный /start
при ожидающей привязке не создаёт вторую запись человека. После подтверждения
отправьте /start в Telegram: компания, роль и история будут общими.
MAX-команды `/link_confirm ID` и `/link_cancel ID` принимают только заявки
текущего исходного аккаунта; кнопки формируют их автоматически.

Если оба аккаунта уже зарегистрированы как разные люди, привязка отклоняется.
Слияние существующих данных требует отдельного восстановления; ни код
приглашения, ни /link не должны молча переносить чужую историю.

Обновление требует пересборки обоих контейнеров (Telegram и MAX), поскольку
часть безопасного сценария находится в Telegram-обработчике. Новых миграций
для обратной привязки нет. Полный набор функций двух адаптеров пока различается;
общий профиль не означает автоматическое появление всех функций Telegram в MAX.
