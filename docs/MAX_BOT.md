# Первое подключение MAX

Ветка добавляет отдельный тестовый адаптер MAX к общей базе FIINOPS.
Пользователь определяется через `external_accounts(platform='max')`, а его
компания, роль, проекты и деньги остаются на прежнем внутреннем `users.id`.
Код Telegram-обработчиков в адаптер не импортируется.

## Подготовка бота и токена

Создайте бота на официальной [платформе MAX для бизнеса](https://business.max.ru/self)
или через [MAX для бизнеса](https://max.ru/business_bot), согласно доступному
вашему профилю процессу. Полученный токен относится только к MAX.

В облачной среде добавляется секрет с именем **MAX_BOT_TOKEN**, переменная
`MAX_BOT_TOKEN`, разрешённый адрес назначения **platform-api2.max.ru**.
Токен не нужно отправлять в чат, записывать в GitHub или в браузерную демопанель.
На собственном сервере можно использовать закрытый `.env` с правами 0600.

Документация MAX проверена 26.10.2026: текущий API использует новый хост
`platform-api2.max.ru`, а авторизация передаётся заголовком `Authorization`.
Параметры query для токена не используются. Запросы не перенаправляются на
другие хосты. При необходимости `MAX_CA_BUNDLE` указывает PEM-файл доверенных
корневых сертификатов; он дополняет системный trust store. Проверка TLS включена.
Сертификаты берутся из официального доверенного источника, не из сообщений бота.

Проверка токена и текущих подписок без изменения БД и получения обновлений:

```bash
python -m app.max_bot --check
```

Команда не меняет Webhook-подписки и не выводит токен. Без настроенного токена
она завершится с понятным сообщением до обращения к MAX и PostgreSQL.

## Тестовый запуск

MAX разрешает Long Polling для разработки и тестирования. Он не требует
публичного входящего адреса, поэтому подходит для первого теста в этой среде.
Для production официальная документация требует Webhook. **Webhook в этот
первый адаптер не входит**, его подключение — следующий этап.

Перед первым запуском сделайте резервную копию существующей базы. Миграция
`011_max_poll_offsets.sql` добавляет только отдельную таблицу курсоров.
Подключение к БД должно указывать на ту же базу, что и Telegram-бот.
MAX требует только `MAX_BOT_TOKEN` и настройки `POSTGRES_*` (при необходимости
`MAX_CA_BUNDLE`). Ключи Telegram/OCR/DeepSeek и `BOT_OWNER_TELEGRAM_ID` ему не нужны.
Инициализация БД не меняет владельца. Синхронизация сохранённой роли владельца
выполняется явно при запуске Telegram; отсутствующий или нулевой ID отклоняется
без изменения ролей. Проверки полномочий Telegram и веб-панели продолжают
использовать настроенный ID владельца.

```bash
python -m app.max_bot --poll-dev
```

При действующей Webhook-подписке polling не запускается и подписка не удаляется.
Один MAX-бот может иметь только один процесс polling: это проверяется блокировкой
PostgreSQL. Разные боты имеют отдельные курсоры.

Курсор сохраняется после завершения всей страницы событий. При временной
сетевой ошибке или HTTP 429/5xx текущая страница остаётся в памяти: уже завершённые
события пропускаются, незавершённое обрабатывается повторно с новой проверкой прав.
Ответы с финансовыми данными не кешируются между попытками. HTTP 403 именно при
отправке сообщения означает недоступность диалога: ответ пропускается с записью
без содержимого сообщения в журнал, остальные пользователи обслуживаются дальше.
HTTP 401, прочие неизвестные 4xx, ошибки обработки и БД завершают процесс;
403 при чтении обновлений также считается ошибкой всего подключения.

При обнаружении разрыва соединения, удерживающего PostgreSQL-блокировку, текущая
работа отменяется и процесс завершается. Автоматического продолжения без блокировки
нет. Новый процесс получает блокировку заново и читает сохранённый курсор.

Подтверждение получения денег защищено идемпотентностью финансового ядра.
Повтор `/link` с тем же действующим кодом от того же MAX-аккаунта возвращает
существующую заявку и не расходует лимит новых попыток. Другой аккаунт,
отменённая заявка и истёкший код отклоняются. Подтверждение исходным аккаунтом
остаётся обязательным; повтор заявки не выдаёт права.

Ограничения тестового режима: после аварийного перезапуска возможны повторные
ответы, в том числе части длинного ответа. Пропущенный ответ в недоступный диалог
автоматически не пересылается. На первом запуске без курсора MAX отдаёт последнее
событие, а не архив; потеря процесса до первого сохранения курсора может потерять
необработанное событие. Прогресс внутри страницы хранится в памяти, не в БД.
Постоянная эксплуатация требует Webhook с долговечной очередью и политикой
повторной доставки — это отдельный следующий этап.

## Связать существующего пользователя

1. В Telegram: «Мой профиль» → «Код для подключения MAX».
2. В личном диалоге с новым MAX-ботом: `/link КОД`.
3. Вернуться в исходный Telegram-профиль и подтвердить показанный MAX-аккаунт.
4. В MAX отправить `/start` или `/profile`.

До шага подтверждения финансового доступа нет. Сам `/start` не регистрирует
дубликат пользователя, не назначает компанию или роль. Invite-код компании
не является кодом привязки аккаунта. Групповые сообщения и сообщения от ботов
игнорируются; ID из текста или пересланного сообщения не определяет пользователя.

## Доступные команды первого этапа

| Команда | Результат |
| --- | --- |
| `/start`, `/help` | Список команд или инструкция подключения |
| `/profile` | Связанные аккаунты и внутренний ID |
| `/projects` | Все неархивные проекты доступной компании |
| `/money` | Последние 30 выдач: свои у сотрудника, компания у руководителя |
| `/balance` | Подтверждённые остатки и задолженность компании |
| `/advance ID` | Карточка доступной выдачи и состояние расходов |
| `/receive ID` | Подтвердить фактическое получение своей выдачи |
| `/report month`, `/report week`, `/report all_time` | Денежный отчёт с теми же правилами и UTC-периодами, что в других интерфейсах |

Сотрудник не получает доступ к чужим выдачам, владелец системы автоматически
не становится руководителем компании. При отключении пользователя MAX теряет
доступ к его данным. Ответы отправляются лично аутентифицированному отправителю.

## Следующие этапы

- HTTPS Webhook с проверкой секретного заголовка, очередью и повторной доставкой.
- Кнопочное меню, выдача денег руководителем и согласование расходов/возвратов.
- Загрузка фото через MAX и подключение к общему документному/OCR-сценарию.
- Полный набор административных действий и уведомления MAX.

Тесты используют поддельный HTTP transport MAX и отдельные временные PostgreSQL.
Реальный токен и реальное сообщение MAX для автоматических тестов не нужны.
Рабочий MAX-бот в этой задаче не запускался: секрет ещё не подключён.

Критерии приёмки рефакторинга:

- отказ одного получателя не останавливает другие диалоги;
- после потери блокировки старый процесс не продолжает polling, новый может стартовать;
- временный сбой не повторяет уже завершённые события в текущем процессе;
- повтор привязки не создаёт событие или пользователя повторно и не обходится без подтверждения;
- отключение пользователя проверяется заново при повторной обработке;
- MAX запускает БД и читает общий учёт без ключей других интеграций;
- запуск MAX сохраняет роль владельца даже при отсутствующей или отличающейся настройке ID;
- справочник проектов использует общий сервис проверки активного членства;
- полный набор тестов Telegram, MAX, финансового ядра и веб-панели проходит.

Проверка после рефакторинга 26.10.2026: **188 тестов прошли без ошибок и пропусков**,
включая 34 проверки MAX (15 новых сценариев надёжности). Проверены реальный разрыв
тестового PostgreSQL-соединения, освобождение блокировки, повтор привязки после
перезапуска, ошибки отправки, отзыв доступа между попытками и независимый запуск
БД без ключей интеграций. `pip check`, компиляция Python и `git diff --check` прошли.
