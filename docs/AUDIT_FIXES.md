# Исправления аудита 30–31.10.2026

Исходная версия `7019bc9` сохранена в GitHub в ветке
`refactor/core-boundary-contract`. Исправления подготовлены отдельно:
`fix/audit-performance`. Финансовые формулы, качество PDF/JPEG и выбранные
провайдеры не меняются. Прежние незавершённые локальные правки диагностики голоса
из исходного worktree в эту ветку не переносились.

## Изменения

- Общий `ReportCommands` для TG/MAX: единый результат на действие, выбор участника
  (руководитель, бывшие сотрудники, люди без документов), страницы и периоды.
  Старые callback-кнопки и нативная выдача XLSX Telegram поддерживаются.
- Компактные SQL-сводки и списки не читают OCR/preview и все товарные позиции.
  Детальная карточка и полный отчёт доступны отдельно. MAX-подсказка о скачивании
  Excel проверяет доступ без расчёта полной выгрузки.
- Ожидающие расходы/возвраты агрегируются заранее; миграция 029 добавляет
  недостающие индексы. Сборка денежных данных использует одно соединение снимка.
- XLSX сохраняется один раз вне event loop; максимум два обычных экспорта и два
  бухгалтерских архива одновременно на процесс. Отмена, включая повторную,
  ждёт окончания файлового потока до освобождения слота/временных файлов.
- Черновик не загружает BYTEA при навигации. Оригинал переносится внутри БД
  `INSERT ... SELECT` в транзакции сохранения документа.
- Оригиналы архива читаются пакетами до 128 файлов/~8 МиБ (один файл до 20 МиБ),
  временно сохраняются на диск; ZIP использует spooled-файл. Итоговый bytes-ответ
  до 45 МиБ остаётся совместимым с Telegram/HTTP, так что память ответа не нулевая.
- Истёкшие черновики очищаются каждую минуту ограниченными пакетами с
  `FOR UPDATE SKIP LOCKED`; все bootstrap-процессы останавливают задачу до БД.
- `DOCUMENT_PROCESSING_CONCURRENCY=4` ограничивает скачивание/OCR на процесс,
  ожидание входит в общий 750-секундный бюджет. После ожидания перепроверяются
  доступ, компания и существование черновика. Подготовка vision-фрагментов —
  максимум две одновременно вне event loop. Разрешённый диапазон настройки 1–16.
- HTTP-клиенты переиспользуются между страницами документа и закрываются после
  операции. Явный OCR-прокси имеет отдельный пул; DeepSeek не наследует его.
- Удаление задания AssemblyAI остаётся ожидаемым best effort, но ограничено 1 с
  вместо обычного сетевого таймаута 25 с. При неудаче сохраняется безопасный лог.
- Нули отличаются от неизвестных значений бухгалтерского Excel; HTML-значения
  Telegram экранируются; валюты не складываются в общий рублёвый итог карточки.
  Отрицательная фискализация берётся из служебной пометки, не названия товара;
  противоречивые реквизиты дают «Не определено». Проверки ФНС не добавлены.
- Удалён неиспользуемый DeepSeek normalize-проход и его cleanup prompt. Тонкие
  совместимые адаптеры оставлены: они не создают второй расчёт или OCR-вызов.

## Доставка MAX

Миграция 028 добавляет inbox/outbox. Страница событий сохраняется вместе с
checkpoint, до выполнения команд. Незавершённая очередь ограничена 1000 записями;
при заполнении получение приостанавливается без продвижения курсора страницы.
Два слота зарезервированы для быстрых меню, четыре — для фоновых событий.
Порядок событий одного MAX-пользователя сохраняется между обеими очередями.

Подготовленный ответ сохраняется до HTTP-отправки; повтор отправляет его заново
после проверки актуального доступа, не исполняя команду повторно. Завершение
очищает текст/медиа/ответ, остаётся небольшой ключ дедупликации на 30 дней.
HTTP-ответ может повториться после потери подтверждения доставки — это не обещание
exactly-once отправки сообщений.

Если процесс упал между началом обработки команды и сохранением ответа, итог
может быть неопределённым. Такая команда автоматически не исполняется повторно:
пользователю предлагается проверить состояние операции через главное меню.
Для документов разрешено восстановление только при наличии канонической записи
начатой загрузки той же компании. Готовый OCR/сохранённый документ не удаляются.
Миграция 030 связывает новые загрузки с компанией; старые события без надёжной
привязки автоматически не восстанавливаются.

Миграция 031 сохраняет привязку финансового ввода к событию и результату в одной
транзакции с операцией. Повтор старого текста MAX не потребляет новую ревизию,
начатую через Telegram. Неуспешная валидация также привязывается к событию, а
частичная запись откатывается через savepoint. Сырые тексты ввода не хранятся.

## Развёртывание и откат

1. Проверить текущую ветку/локальные изменения и сохранить резервную копию БД.
2. Собрать Telegram/MAX/web из `fix/audit-performance`.
3. Остановить старые процессы Telegram/MAX/web, поднять новые вместе. Миграции
   028–031 применяются автоматически под общей блокировкой. Сброс БД не нужен.
4. Проверить здоровье панели, polling обоих ботов, отчёты и тестовую загрузку.

Перед откатом на старый MAX-процесс обязательно дождаться пустой незавершённой
inbox-очереди либо подготовить отдельное воспроизведение сохранённых событий.
Старый poller игнорирует inbox, а транспортный курсор новой версии уже продвинут
после сохранения событий. Один откат кода/БД не возвращает удалённый курсор MAX.
Нельзя удалять inbox ради отката или запускать два poller для одного токена.

## Проверка

Проверки выполняются на временных PostgreSQL-базах, не на данных VPS; HTTP
провайдеров заменён управляемыми ответами. Помимо функциональных регрессий
проверяются очереди, повторные/конкурентные сообщения, смена прав/компании,
восстановление OCR, перезапуск, rollback, размеры SQL-ответов и отзывчивость
цикла событий при экспорте. Это не нагрузочное подтверждение 1000 активных людей
и не проверка лимитов реальных OCR/LLM-тарифов.

Итог проверки: полный прогон — 553 теста, успешно; дополнительный набор —
34 проверки, включая позднее добавленные сценарии неопределённого повтора,
смены доступа при подготовке ответа и подписи к изображению при активном вводе
карты. Синтаксис JS и git diff --check проверены.

Локальные синтетические замеры (не VPS): денежный SQL на 1000 выдачах/10000
возвратах — 929 мс до изменений и 205 мс после; обычный XLSX на 2000 документах /
10000 позициях — около 1,14 с, максимальная пауза heartbeat около 0,48 с против
прежних 1,84 с. Executor не исключает полностью конкуренцию за Python GIL/GC;
для более крупных нагрузок остаётся возможность выделенного процесса/worker.
