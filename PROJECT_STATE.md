## Что реализовано

- PostgreSQL, канонический users.id, привязки Telegram/MAX и отдельные приглашения
  в компанию. Вступить можно на выбранной платформе, без Telegram для MAX-first.
- Owner администрирует сервис; manager ведёт свою компанию, employee — свои данные.
  Один активный manager на компанию, одна активная компания на пользователя,
  до 10 активных сотрудников. Owner не становится manager автоматически.
- Проекты active/archived; ролевое меню, имена/названия и скрытые callback ID.
- Общий DocumentFlow Telegram/MAX: фото/PDF, настройка DeepSeek Vision/OCR.space,
  структура, предпросмотр, проекты, дубли включая архив, проверка сумм, сохранение.
- Сохранённые затратные документы входят в затраты независимо от источника оплаты.
  Привязки к выдаче/карте задают расчёт и не создают вторую сумму затрат.
- Выдачи/получение/расходы/возвраты, бизнес-карты, отчёты/Excel; интерфейсы неравны
  по возможностям — матрица находится в PRODUCT.md.
- Web owner/manager, Telegram Mini App, ИИ-вопросы голосом/текстом Telegram.
- SQL-миграции 001–022, durable-черновики, ключи повторов, аудит и backup-скрипт.

## Архитектурные границы

Ядро — общий Python-код, не отдельный контейнер. Тестовый профиль двух ботов:
PostgreSQL + Telegram + MAX. Веб-панель и Caddy — дополнительные сервисы.
В адаптере остаются аутентификация платформы, файлы, сообщения и кнопки.
Ядро документов импортируется/создаётся без Telegram SDK; старые API некоторых
сервисов сохранены как совместимые фасады. Не копировать бизнес-правила в новый бот.

## Ограничения и последующие задачи

- MAX poll-dev: последовательная обработка OCR, без production Webhook/worker.
- MAX не имеет полного интерфейса карт, возвратов и ИИ-запросов Telegram.
- Готовый черновик живёт 15 минут и переживает рестарт. Сбой посреди OCR требует
  отмены/повторной отправки исходника; оригиналы не архивируются.
- Нет редактора распознавания, импорта выписок, банковских переводов, бюджетов,
  выручки/прибыли, MAX Mini App и браузерного кабинета сотрудника.
- Runtime-развёртывание, мониторинг и расписание backup проверяются отдельно.

## Проверки и обновление

На срезе `69c2842` полный прогон — 373 теста, успешно. Это история проверки кода;
внешние OCR/LLM в автотестах подменены. Не считать её проверкой живого VPS/API.
Интеграции запускаются с RUN_DATABASE_TESTS=1, отдельной PostgreSQL и CREATEDB
для тестового пользователя. Без флага интеграционные тесты пропускаются.

Перед миграцией 022 нужна копия БД и остановка старых процессов, работающих с
хранилищем черновиков. Имя Compose-проекта/том и рабочий .env сохраняются.
Для обычного обновления не удалять том данных и не менять рабочую БД пустой.
