# ZATRATPRO

MVP Telegram-бота для распознавания чеков, актов и накладных.

## Веб-панель управления

[Открыть демо интерфейса](https://akizyakov-arch.github.io/zatratpro/) —
вымышленные данные, без подключения к рабочей базе.

Веб-панель FIINOPS для руководителя и владельца системы использует общую базу
и ядро с ботом. Вход подтверждается в Telegram. В панели доступны выдачи,
расходы и возвраты, бизнес-карты, документы, проекты, сотрудники, отчёты и Excel.

[Запуск и обновление панели](docs/WEB_PANEL.md) ·
[Функциональные требования](docs/WEB_PANEL_REQUIREMENTS.md).
Перед первым запуском обновите бот совместно с панелью и сделайте резервную копию БД.

## Что умеет каркас

- запускает Telegram-бота на `aiogram`
- обрабатывает `/start` и `/help`
- принимает фото
- скачивает файл во временную папку `tmp/`
- отправляет фото в OCR.Space
- передает OCR-текст в DeepSeek
- валидирует JSON по контракту документа

## Требования

- WSL2 Ubuntu
- Python 3.11+
- Telegram Bot Token
- OCR.Space API key
- DeepSeek API key

## Надёжность и состояние

При запуске после подключения к PostgreSQL автоматически применяются версионированные
миграции из `db/migrations/` в транзакции с блокировкой. Они добавляют новые поля и
таблицы, не удаляя существующие документы. При первом создании БД по-прежнему нужна
исходная схема `db/init/001_init.sql` (Docker Compose применяет её автоматически).
Пользователю БД нужны права на изменение схемы. Перед обновлением сделайте резервную
копию БД. Docker-образ включает файлы миграций.

Черновики документов и незавершённые действия хранятся в PostgreSQL с TTL 15 минут.
Они переживают перезапуск; истёкшие записи недоступны и очищаются при запуске и новых
операциях. Если процесс прервётся во время самого OCR/LLM-запроса, этот запрос не
возобновляется автоматически. Повторный callback одной загрузки не создаёт вторую
запись, при этом отдельно загруженные одинаковые документы можно осознанно сохранить.
Кнопки привязаны к конкретной загрузке; старые кнопки не изменяют новый черновик.

Единственный действующий владелец задаётся `BOT_OWNER_TELEGRAM_ID`; сохранённая роль
прежнего владельца не даёт доступа после смены ID и перезапуска. Обрабатываемые
фотографии считаются временными и удаляются после OCR, включая ошибки. Архив
оригиналов эта версия не ведёт. Excel-экспорт сохраняет пользовательские строки
как текст, а диагностические логи скрывают известные секреты и токены Telegram.

## Тесты

Без внешних API и без PostgreSQL:

```bash
python -m unittest discover -s tests -p 'test_unit.py' -v
```

Полный набор (пользователь PostgreSQL должен иметь право `CREATEDB`):

```bash
# POSTGRES_HOST, POSTGRES_PORT, POSTGRES_USER, POSTGRES_PASSWORD задайте в окружении.
RUN_DATABASE_TESTS=1 python -m unittest discover -s tests -v
```

Тесты создают отдельную базу со случайным именем `test_zatratpro_*` для каждого
сценария и удаляют её после проверки. `POSTGRES_DB` не используется как тестовая
база. Тесты не отправляют сообщения в Telegram и не вызывают OCR.Space/DeepSeek.
Проверяются гонки приглашений/лимита сотрудников, идемпотентность сохранения,
изоляция компаний, смена владельца, восстановление состояния, маршрутизация
callback, очистка файлов и типы ячеек XLSX. При отсутствии `RUN_DATABASE_TESTS=1`
интеграционные проверки явно пропускаются.

## Деньги на закупки

В меню руководителя и сотрудника доступен раздел **Деньги на закупки** (`/advances`).
Руководитель выбирает сотрудника и проект кнопками, затем вводит сумму в рублях
и назначение. Сотрудник открывает свою выдачу и подтверждает фактическое получение.
Раздел учитывает реальные передачи денег; банковские переводы не выполняются.

После обычной загрузки и сохранения чека сотрудник открывает выдачу → «Приложить
чек». Подходят только его документы той же компании и проекта в RUB; один чек
нельзя списать на две выдачи. Руководитель принимает расходы в карточке выдачи.
Сотрудник заявляет фактический возврат, руководитель подтверждает его.

Остаток = выданная сумма − принятые расходы − подтверждённые возвраты.
Неодобренные операции не меняют остаток. Отрицательный остаток — перерасход,
который компания должна сотруднику. Повторные подтверждения идемпотентны;
согласование возвратов сериализуется в БД и не позволяет вернуть больше остатка.
История действий хранится в `advance_events`, денежные суммы — в NUMERIC/Decimal.

Первая версия не содержит банковской интеграции, отмены/сторно согласованных
операций, разделения одного чека между выдачами и межпроектных переводов. Перед
использованием проверьте выбранного сотрудника, сумму и назначение. Список
показывает последние 30 выдач. Незавершённый ввод можно отменить командой `/cancel`.
Миграция `002_employee_advances.sql` применяется вместе с остальными при запуске.

### Деньги на руках

Кнопка «Деньги на руках» или `/balance` показывает сводку по всем проектам:
подтверждённое получение минус принятые расходы и подтверждённые возвраты.
Сотрудник видит только свои суммы, руководитель — сотрудников своей компании.
Выдачи, получение которых ещё не подтверждено, показаны отдельно. При перерасходе
на руках показан ноль, а задолженность компании сотруднику — отдельной строкой.

### Отчёт по деньгам

«Деньги → Отчёт по деньгам» или «Отчёты → По деньгам»: выберите период, включая
«Всё время». Получение учитывается по received_at, расходы и возвраты — по дате
подтверждения руководителем. Начальный остаток включает движения до периода,
конечный = начальный + получено − принятые расходы − возвраты. Неполученные
выдачи, расходы и возвраты на проверке показаны отдельно и не уменьшают остаток.
Даты периодов совпадают с существующими отчётами (UTC). Сотрудник видит свои
деньги, руководитель — компанию с разбивкой по сотруднику и проекту.
Денежная сводка также добавлена к отчётам проектов и сотрудников; в общей
Excel-выгрузке — лист Money и показатели на Overview. Документные затраты
остаются отдельно: сумма выдачи не является дополнительным расходом.

## Бизнес-карты

«Деньги → Бизнес-карты»: руководитель добавляет название карты и последние 4 цифры.
Сотрудник сначала загружает чек и выбирает проект обычным способом, затем в разделе
карт нажимает «Указать оплату чека картой», выбирает чек и карту. Руководитель
принимает расход кнопкой. Подтверждение — проверка руководителем, не сверка с банком.
Полный номер карты, срок и CVV не требуются и не хранятся в таблице карт.

Один документ нельзя одновременно привязать к выдаче и карте; проверка защищена
блокировкой документа и работает при конкурентных запросах. Сумма берётся из
сохранённого чека, отдельно не вводится. Это расходы компании, они не изменяют
остатки подотчётных денег. Карты доступны активным участникам своей компании,
ограничение отдельных карт конкретным держателем пока не введено.

Денежные отчёты и сводки проектов/сотрудников отдельно показывают карточные
расходы и суммы на проверке. Excel содержит лист BusinessCards и показатели
на Overview. Стандартная сумма расходов по документам не увеличивается второй
раз из-за карточной привязки. Дата принятия используется для периода отчёта.
Импорт банковских выписок, сверка с банком, карточные возвраты, смена источника
оплаты уже привязанного чека и дробление оплаты пока не реализованы.

## Профиль и привязка аккаунтов

«Мой профиль» (`/profile`) работает только в личном чате. Существующие Telegram
аккаунты мигрируются в `external_accounts` с сохранением внутренних users.id.
Новые Telegram-регистрации также создают эту привязку. У одного пользователя
может быть по одному аккаунту Telegram/MAX/веб; внешний аккаунт принадлежит
ровно одному внутреннему пользователю.

Сервис `AccountLinkService` не зависит от SDK мессенджера. Адаптер передаёт ему
только проверенные платформой ID отправителей, никогда ID из текста пользователя:
`issue(source_platform, source_external_id, target_platform)` → одноразовый код;
`claim(target_platform, target_external_id, code)` → заявка без предоставления
доступа; `confirm(source_platform, source_external_id, request_id)` → привязка.
В Telegram для ввода кода из другой платформы есть `/link КОД`. Этот маршрут
не создаёт новую пользовательскую запись до подтверждения.

Код действует 5 минут, хранится в виде SHA-256-хеша и используется один раз.
Для предъявляющего аккаунта допускается 5 попыток за 15 минут, включая неверные
коды. Новый код для той же платформы отменяет предыдущий. Подтверждение
возможно только через тот исходный аккаунт, который выпустил код; компания,
роль и финансовые записи остаются у прежнего users.id. Занятые аккаунты
не переносятся и пользователи автоматически не объединяются.

Заявка автоматически отправляется исходному Telegram-аккаунту фоновым
доставщиком; её также можно проверить/отклонить в профиле. Доставка при сбоях
повторяется; повторные уведомления при аварии между отправкой и фиксацией
возможны, но подтверждение идемпотентно. История хранится в account_link_events
без исходных кодов. Для исходной платформы MAX/веб доставка подтверждений
потребует соответствующего адаптера.

Первый [тестовый адаптер MAX](docs/MAX_BOT.md) добавляет привязку, просмотр
проектов и денег, отчёты и подтверждение получения. Для реального подключения
нужен отдельный `MAX_BOT_TOKEN`. Production Webhook, загрузка документов через
MAX и остальные сценарии остаются следующим этапом.
Приглашение в компанию, привязка второго аккаунта и восстановление потерянного
аккаунта — разные операции. Автоматического восстановления без исходного
аккаунта и удаления последней привязки в этой версии нет.

## Границы финансового ядра и результаты проверки

[Анализ и рефакторинг](docs/REVIEW_REFACTOR.md) описывает исправленные проблемы,
границы ядра и ограничения. Финансовые сервисы принимают внутренние user ID;
Telegram-разрешение аккаунта и отправка отчётов находятся в `app/handlers/`.
Read-модели выбора сотрудников/проектов вынесены в `FinanceDirectory`, периоды
отчётов — в общий модуль. Агрегированный отчёт читает подотчёт и карты из одного
снимка PostgreSQL и отдельно показывает деньги сотрудников и задолженность компании.
При переносе вызовов используйте `get_money_report_for_user(user_id,start,end)`
из `app.services.money_reports`; Telegram-обёртка — `app.handlers.money_reports`.

Запросы ввода имеют ревизии, чтобы поздний ответ не удалял новый запрос. Доставка
заявок привязки использует аренду: соединение БД не занято во время Telegram-запроса,
при сбое предусмотрена задержка повторной доставки. Отключённые пользователи не
могут пользоваться финансовыми функциями и действиями владельца. Изменения требуют
штатного запуска новых миграций 005–007, с резервной копией перед обновлением.
